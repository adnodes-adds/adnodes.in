Building an app with Claude Code, without being a coder

9 OCTOBER 2026 · K. THANGAMANI PRABU · PART 1 OF 2

I have been building with Claude Code for some months now, and I will say it plainly: I spent more than I should have. Most of what I followed came from social media posts and short videos, each one promising a single trick that makes the agent build a full app in one go. It does not work like that, at least not for me. I paid for the confusion in tokens.

This post is what I do now. Nothing in it is clever. It is a small set of habits, and almost every one of them I later found written in Anthropic's own documentation, which I should have read first.[1] I am not a programmer, so I have tried to write this for someone like me, with every technical word explained.

The idea I build with: screens, slices, agents

A screen is what you see in the app, for example a main screen or a settings window. A slice is one small piece of a screen that I can test by clicking, like "the Save button stores the entry". Wiring is the connection between them: which button opens which pop-up. Agents are the helpers that do the work, and I keep only three: a planner that makes the plan before any code, a builder that builds one slice, and a tester that checks it afterwards.

Claude Code supports this directly. A subagent is just a markdown file inside .claude/agents/ with a name, a description and, if you want, the model it should use.[3] That model line is where the saving is. I put the planner on a stronger model, the builder on Sonnet and the tester on Haiku, because checking is cheaper work than planning.[6]

Why not ten agents? I tried that also. More agents meant more tokens and more places for things to go wrong. Anthropic's note on building agents says the same thing: start with simple patterns and add complexity only when it clearly helps.[10]

Set up the folder before touching Claude

  1. Make a folder for the app, say my-new-app.
  2. Inside it make a folder called research and put all your notes, screenshots and reference files there.
  3. Open a terminal in my-new-app and type claude.
  4. Press Shift+Tab until the bottom line says plan mode. In plan mode Claude reads and proposes, but it does not edit anything until you approve.[7]

The first prompt: documents only, no code

My first session never writes code. It only creates the documents that will guide every later session. This is the shortened version of what I paste:

I am a non-technical founder. In this session do not write any app code.
We are only setting up documents.

The app idea: [one paragraph in plain words]

1. Read my notes in research/ (read-only, never edit them). Create
   research/INDEX.md with one line per file, and research/SUMMARY.md with
   a section "Contradictions and gaps".
2. Create PRODUCT.md, STATUS.md, AGENTS.md, docs/SPEC.md, docs/PLAN.md,
   docs/COSTS.md. Make CLAUDE.md contain only one line: @AGENTS.md
3. In PRODUCT.md: what the app is, who it is for, top 5 features, what it
   must never do, what "done" means for version 1 as a checklist I can
   click, what is not in version 1, open questions.
4. In docs/PLAN.md: 6 to 10 thin slices, each testable by me by clicking.
   First slices use fake data, so no money is spent until the app works.
5. In docs/COSTS.md: estimate the AI cost of one job. Show the maths step
   by step and mark the assumptions.

Finish by showing me PRODUCT.md, the open questions, the cost estimate and
the slice plan. Then stop and wait for my approval.

About CLAUDE.md: Claude Code loads it at the start of every session, so everything in it costs tokens every time. The docs suggest keeping it under about 200 lines.[2][6] Mine contains one line that imports a second file, AGENTS.md, where the real rules sit. The memory page describes this import method for people who share one rules file across tools.[2] You can also run /init and let Claude write a starter CLAUDE.md by scanning the project.[8]

Read what comes back, edit PRODUCT.md yourself, and answer the open questions. That file is yours. Do not let the agent decide what your product is.

After that, every slice is a fresh start

  1. Type /clear. It starts a new conversation with empty context. Your files keep the memory, the chat does not need to.[8]
  2. Paste the slice prompt (below).
  3. Read the short plan Claude shows and approve it.
  4. Let it build only that slice.
  5. Ask: "Run the checks for this slice and tell me pass or fail."
  6. Click through it yourself, the way a user would.
  7. Type /usage and note the cost. (/cost is the same command under another name.)[8]
Start Slice [N]: [name from docs/PLAN.md].
Read AGENTS.md, PRODUCT.md, STATUS.md and the part of docs/SPEC.md for
this slice. Show a short plan: what you will build, which agent does it,
how I will test it by clicking, and the risks. Wait for my approval.
Build only this slice. Run the app and tests and show me the results.
Update STATUS.md. Then tell me in plain English what I should click.

The rule that saved me most money is simple: never trust the word "done". Claude can say it with full confidence while nothing works. Anthropic's best-practices page says giving Claude a way to check its own work, like tests or a screenshot, is the single best thing you can do.[1] Since I cannot read the code, I ask for the test results and for what to click.

Keeping the bill reasonable

These are the habits that made a real difference, and most of them match the cost page in the docs.[6]

  • Sonnet by default. Opus only for hard planning, and I justify it to myself before switching. Haiku for simple subagent jobs.[6][9]
  • Short sessions. One slice, then /clear. If a session must run long, /compact with a focus line, for example "focus on the next slice", and check /context to see how full it is.[8]
  • Thin slices with fake data first. I do not connect any paid service until the app already works with dummy data.
  • Predict before you spend. After slice 1, I look at /usage and multiply by the number of slices left. If that number is scary, I know it in week one, not in week six.
  • Few MCP servers. Every connected tool adds to what Claude carries. Where a command-line tool such as gh does the same job, I use that instead.[6]
  • Ideas go to a parking file. When I think of a new feature mid-slice, I say "add to docs/IDEAS.md, do not build it". Building it right then is how a slice becomes three.

For overnight work there is /schedule, which runs routines on Anthropic's cloud. It is a research preview, it counts against subscription usage, and there are hourly limits, so I have not started using it yet.[11]

What I stopped doing

I stopped writing one giant prompt and hoping. I use to think a bigger prompt gives a better result, but it only gave me bigger mistakes to correct. I stopped keeping a long CLAUDE.md, because the docs warn that a bloated one makes Claude ignore parts of it.[1] And I stopped relying on a "dreaming" memory feature I had read about online. I could not find it in the Claude Code documentation, so I left it out. Every five slices I do something plainer: I ask Claude to read my notes from the last five slices and propose up to five new one-line rules, and I approve them myself.

Where this goes next

This basic structure is enough for the first few slices. When the project grows, a few more files help a lot. That is the second part: a sturdier folder structure for Claude Code projects.
