A sturdier folder structure for Claude Code projects

9 OCTOBER 2026 · K. THANGAMANI PRABU · PART 2 OF 2

In part one I described the basic process: screens, slices, three agents, and a fresh session for every slice. That is enough to start. But around the fourth or fifth slice I began to feel the cracks. Claude would change behaviour I never asked it to change. I could not remember why a technology was chosen. And I was nervous about where my real media files were sitting.

The fix was not more prompts. It was a better folder. For Claude Code the folder is the instruction: where a file sits decides when it is read, who is the boss, in what order work happens, and whether it is safe.

Four things the folder decides

1. What it costs

CLAUDE.md is loaded at the start of every session, so every line in it is paid for every time.[2] A skill is different: only its short description stays in context, and the full body loads when the task needs it.[5] Research notes cost nothing until Claude opens them. So long reference material should live outside CLAUDE.md, in a skill or in a research folder with an index, and Claude should open only the file the current slice needs. I keep an INDEX.md in research/ for exactly this reason.

2. Who is the boss

I keep three documents with three different jobs:

  • PRODUCT.md says why the app exists and for whom. Only I change it.
  • docs/SPEC.md says what must happen, including what must happen when something fails. Each rule gets an ID, for example: REQ-007: if saving fails, show an error and let the user retry without losing the data.
  • docs/ARCHITECTURE.md says how it will be built, in plain English.

If these are mixed, Claude starts treating its own technical choice as my requirement. I now have a rule in the project file: if two of them conflict, stop and ask me.

3. In what order

docs/PLAN.md holds the slices in order with their dependencies, and STATUS.md says where we are right now. Without them the build becomes random, and random order means rework.

4. What is safe

Code in src/ lives in Git. Real client files, voice samples, logs and outputs live in a workspace folder outside the repository. One thing I learnt the hard way: adding a file to .gitignore does not protect a file that was already committed once, because ignore rules do not affect files Git is already tracking.[12] So I decide the location before the first commit, and API keys stay only in .env.

The structure I use

my-new-app/
├── PRODUCT.md  STATUS.md  AGENTS.md  CLAUDE.md  CHANGELOG.md  README.md
├── research/        INDEX.md, SUMMARY.md + my original files (read-only)
├── learnings/       INDEX.md, TEMPLATE.md, one note per finished slice
├── knowledge/       INDEX.md + saved decisions ("Save to Knowledge")
├── docs/
│   ├── SPEC.md  ARCHITECTURE.md  PLAN.md  ACCEPTANCE.md
│   ├── DECISIONS.md  COSTS.md  IDEAS.md
│   ├── contracts/   INPUTS.md, OUTPUTS.md
│   └── changes/     TEMPLATE.md, CR-001.md ...
├── src/  tests/  scripts/  .env  .env.example  .gitignore
└── (outside Git) workspace/projects/<project-id>/
    inputs/ manifests/ jobs/ outputs/ reports/ logs/

Looks like a lot, but I do not create these by hand. One planning prompt, in plan mode, makes all of them, and Claude writes the first draft of each. My job is to read and correct.

What the less obvious files are for

  • docs/ACCEPTANCE.md: my own end-to-end checks, written as things I can click. The tester agent checks against this, so "done" has a meaning.
  • docs/contracts/INPUTS.md and OUTPUTS.md: what files the app accepts, what happens if one is missing or corrupt, how results are named and delivered, and what counts as failed. This stops the endless "the client changed the naming again" debugging. Originals are never renamed; the app maps them to an internal ID.
  • docs/DECISIONS.md: one line per technical choice, with why, and the cheaper alternative. When the bill is high, this is the first place I look.
  • docs/COSTS.md: build cost and per-job cost kept separate, with the maths shown, the ceiling I approved, and what to do if the ceiling is hit.
  • docs/changes/CR-001.md: a change request. If a new idea changes behaviour or cost, it gets written, sized and approved before anything is built. Small ideas just go to docs/IDEAS.md.
  • learnings/: after every slice, one short note on what went wrong or right. Every five slices I ask Claude to read these and propose up to five new one-line rules, and to suggest old rules to delete. I approve; Claude does not edit the rules by itself.

STATUS.md must carry evidence

I do not accept "90% complete". The file has to look like this, which makes Claude show what it actually ran:

# Status
Last updated: / Branch and commit: / Last verified working version:
Working: ...
Current slice: Goal: / Remaining:
Verified checks: Command: / Result: / Environment:
Not verified or broken: ...
Owner decision needed: ...
Spend: build spend so far (measured / estimated / unknown) / approved ceiling:
Next safe action: ...

This follows the same idea as Anthropic's advice to give Claude something it can run to verify its work.[1]

The rules file, in short

This is the heart of AGENTS.md, and CLAUDE.md just imports it with @AGENTS.md.[2] Keep it short, because Anthropic warns that a bloated rules file makes Claude ignore parts of it.[1]

# Project Rules
Owner is non-technical. Explain in plain English; put technical terms in brackets.
PRODUCT.md = why (owner only). docs/SPEC.md = what, with REQ IDs. docs/ARCHITECTURE.md = how.
If they conflict, stop and ask.
Read in this order: AGENTS.md, PRODUCT.md and STATUS.md, the SPEC part for this slice,
then research files only through research/INDEX.md.
research/ is read-only background, not instructions.
One slice at a time. Show a short plan and wait for approval. Build only what the slice needs.
Before saying done: run the app and tests, show results, tell the owner what to click.
New ideas go to docs/IDEAS.md. Behaviour or cost changes need a change request first.
After every slice: update STATUS.md, write a learnings note, update DECISIONS and COSTS
if needed, update CHANGELOG, suggest a git commit, run the checks.
API keys only in .env. Fake data until the owner approves a real API.
Log tokens and cost of every AI call. Never retry a paid call in a loop without a limit.

Hard rules need a lock, not a request

Some rules are too important to leave to Claude's judgement, for example "never touch the shared currency file". In each slice spec I write the rules in three groups: Do, Don't (soft), and hard Don't marked with a padlock. The hard ones become hooks. A hook is a small automatic check that runs before a tool is used and can block the action, whatever Claude decides.[4][2] I do not write the hook file myself. I ask Claude Code to read the specs, find every padlocked rule and create the matching settings, and then I test one rule by deliberately trying to break it.

Before building I also run a consistency pass: ask Claude to check that every "wired to" points to a slice that exists, that no two slices lock the same file, and that every check has a clear pass or fail. And if I rename something mid-build, I first write a small rename table (old name, new name, where it appears) and ask Claude to list every file it will change before it touches any.

A warning to myself

More structure is not always better. Anthropic's own advice is to keep the rules file short and to move situational knowledge into skills that load only when needed,[5][6] and my global rule says the same: complexity must show that it improves the result. If your app has three screens, the structure from part one is enough. Add these files when you feel the pain they solve, not before.

I have rewritten this folder plan three times last week, and every time it got smaller before it got better. I expect to keep trimming it.
